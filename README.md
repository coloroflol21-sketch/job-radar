# Job Radar

Мониторинг новых вакансий с уведомлениями в Telegram и отправкой откликов прямо из чата.
Каждые полчаса опрашивает открытое API «Работа в России», отбирает подходящее по зарплате
и стоп-словам, отбрасывает уже виденное и присылает дайджест. Отклик отправляется командой
`/apply A1` с текстом письма — бот сам находит адрес работодателя и отправляет письмо по SMTP.

Работает без сервера и без платных подписок: расписание держит GitHub Actions, состояние
хранится в самом репозитории. Дайджест-сценарий продублирован как workflow для n8n.

![тесты](https://img.shields.io/badge/tests-155%20passing-brightgreen)

## Зачем

Открывать сайты вакансий каждый день — рутина, а хорошие предложения закрываются за пару суток.
Радар делает это сам, присылает только то, что раньше не показывал, и позволяет откликнуться
из того же чата, не открывая ни сайт, ни почтовый клиент.

## Команды бота

| Команда | Что делает |
| --- | --- |
| `/list` | вакансии, доступные для отклика, с их кодами |
| `/preview A1` | контакты и адрес, куда уйдёт отклик |
| `/apply A1` + текст письма с новой строки | отправить отклик |
| `/sent` | история отправленных откликов |
| `/help` | справка |

Отклик пишется одним сообщением: первая строка — команда, дальше текст письма.

```
/apply A1
Здравствуйте! Заинтересовала вакансия Python-разработчика.
Три года пишу на Python, опыт с Django и PostgreSQL. Резюме прилагаю ниже.
```

Скорость ответа зависит от режима. В режиме живого бота (`npm run bot`) ответ приходит
сразу. При запуске по расписанию в GitHub Actions — при очередном прогоне, в среднем
через 15 минут. Telegram хранит непрочитанные сообщения 24 часа, поэтому команда,
отправленная когда бот не запущен, выполнится при следующем старте и не потеряется.

## Как запустить локально

Нужен Node.js 20 или новее.

```bash
npm ci
npm test              # 155 тестов
npm run check         # проверить настройки: бот, чат, почта, источник
npm run bot           # живой бот: отвечает сразу, пока не остановите
npm run dry-run       # показать найденное в консоли, ничего не отправляя
```

### Два режима работы

`npm run bot` — режим живого бота. Запустили один раз, он присылает вакансии
и отвечает на команды **сразу**, без задержек. Работает, пока открыто окно консоли;
остановить — `Ctrl+C`. В чат приходит уведомление о запуске и об остановке, чтобы
было видно, отвечает бот сейчас или нет.

Интервал поиска вакансий в этом режиме — час, меняется флагом:

```bash
node src/index.js --serve --scan-interval 30
```

`npm start` — один прогон: разобрать накопившиеся команды, поискать вакансии, выйти.
Этот режим используется в GitHub Actions, где программа запускается по расписанию.
Команды тоже работают, но ответ приходит при следующем запуске.

`npm run check` проверяет всё по очереди и говорит, что именно не так: неверный токен,
не тот `chat_id`, обычный пароль вместо пароля приложения. Работодателям при этом ничего
не отправляется — только тестовое сообщение вам в Telegram.

Для реальной работы заполните `.env` (см. ниже) и запустите `npm start`.

Отправка откликов требует доступа к почте (`SMTP_USER`, `SMTP_PASSWORD`). Без них поиск
вакансий работает как обычно, а `/apply` ответит, что почта не настроена.

## Подключение Telegram-бота

1. Напишите [@BotFather](https://t.me/BotFather), отправьте `/newbot` и следуйте подсказкам.
   В ответ придёт токен вида `123456:ABC-DEF...`.
2. Напишите своему боту любое сообщение — без этого он не имеет права писать вам первым.
3. Скопируйте `.env.example` в `.env` и впишите туда токен.
4. Узнайте id чата: `npm run chat-id`

   Скрипт покажет, какому боту принадлежит токен, дождётся вашего сообщения и напечатает
   `chat_id` — впишите его в `.env`. Если `getUpdates` возвращает пустой список, скрипт
   подскажет причину: писали другому боту, установлен webhook или токен не от того бота.

## Файл настроек

Локально настройки берутся из файла `.env` в корне проекта — так они не зависят от того,
запускаете вы команды в Git Bash, cmd или PowerShell, где синтаксис переменных разный.
Образец лежит в `.env.example`, скопируйте его и заполните.

```
TELEGRAM_BOT_TOKEN=8123456789:AAF-xxxxxxxxxxxxxxx
TELEGRAM_CHAT_ID=123456789
SMTP_USER=you@gmail.com
SMTP_PASSWORD=xxxx xxxx xxxx xxxx
SMTP_HOST=smtp.gmail.com
SMTP_PORT=465
```

Пароль приложения Google показывается четырьмя группами по четыре символа — вписывайте
как есть, пробелы допустимы. Кавычки не нужны.

`.env` внесён в `.gitignore` и в репозиторий не попадёт. В GitHub Actions файла нет:
там значения приходят из секретов, и они всегда приоритетнее файла.

Токен — это пароль от бота. Держите его в секретах GitHub или переменных окружения,
никогда не коммитьте в код.

## Настройка почты для откликов

Письма уходят с вашего адреса через SMTP. Обычный пароль от почты не подойдёт —
нужен **пароль приложения**, отдельный пароль для программ.

| Провайдер | `SMTP_HOST` | `SMTP_PORT` | Где взять пароль приложения |
| --- | --- | --- | --- |
| Яндекс | `smtp.yandex.ru` | `465` | Яндекс ID → Пароли приложений → Почта |
| Mail.ru | `smtp.mail.ru` | `465` | Настройки → Пароли для внешних приложений |
| Gmail | `smtp.gmail.com` | `465` | Google Account → App Passwords |

Письма уходят с адреса из `SMTP_USER`. Если нужно отправлять с другого адреса или подписью
вида `Имя Фамилия <me@example.com>`, задайте `SMTP_FROM` — ответы всё равно будут приходить
на `SMTP_USER`.

Для Gmail пароль приложения доступен только при включённой двухэтапной аутентификации.
У всех провайдеров пароль показывается один раз — сохраните его сразу, иначе придётся
создавать новый. Отзывается он там же, независимо от основного пароля.

Для поиска работы в России удобнее Яндекс или Mail.ru: настройка короче, письма с их
адресов реже попадают в спам у российских работодателей.

## Запуск по расписанию в GitHub Actions

1. Создайте репозиторий и загрузите в него проект.
2. В настройках репозитория откройте **Settings → Secrets and variables → Actions**
   и добавьте секреты: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`,
   а для откликов ещё `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_HOST`, `SMTP_PORT`.
3. На вкладке **Actions** выберите **Job Radar → Run workflow**. Для первой
   проверки поставьте галочку `dry_run` — вакансии появятся в логе без отправки в чат.

Дополнительных прав workflow не нужно: в репозиторий он ничего не пишет.

Дальше запуск идёт сам по cron: `*/5 * * * *` — каждые 5 минут, это минимум, который
допускает GitHub. Задержка ответа бота на команды получается в среднем 2,5 минуты.
На публичном репозитории стандартные раннеры бесплатны и квоту не расходуют; на приватном
такая частота съела бы 8640 минут в месяц при лимите 2000, там разумный предел — 15 минут
(`2,17,32,47 4-19 * * *`).

GitHub может отключить cron в репозитории, где 60 дней не было активности — достаточно
зайти и запустить workflow вручную. Также cron иногда стартует с задержкой под нагрузкой,
а часть очереди может отбрасываться: гарантии запуска ровно по расписанию нет.

### Где хранится состояние

Файл `state/` в репозиторий не попадает — он в `.gitignore`. В нём адреса работодателей
и история ваших откликов, которым не место в публичной истории git. Между запусками его
хранит кэш GitHub Actions: шаг восстановления подтягивает последнее сохранённое состояние
по префиксу ключа, шаг сохранения пишет новую запись.

Кэш неизменяем по ключу, поэтому ключ уникален для каждого запуска, а `restore-keys`
находит ближайшую предыдущую запись. Две особенности кэша стоит знать: записи, к которым
не обращались неделю, удаляются, и на репозиторий отведено 10 ГБ. Для нашего файла
в несколько десятков килобайт это не ограничение, но если радар простоит больше недели,
состояние обнулится и первый запуск пришлёт вакансии заново.

## Вариант на n8n

Файл `n8n/job-radar.workflow.json` импортируется через **Workflows → Import from File**
и повторяет ту же логику из пяти нод: расписание → сборка запросов → HTTP-запрос →
отбор и оформление → отправка в Telegram.

Токен и id чата берутся из переменных окружения n8n — задайте `TELEGRAM_BOT_TOKEN`
и `TELEGRAM_CHAT_ID` перед запуском. В self-hosted n8n доступ к `$env` из выражений
включается переменной `N8N_BLOCK_ENV_ACCESS_IN_NODE=false`. Если правило запрещено
политикой вашей установки, замените в ноде «Отправить в Telegram» подстановку `$env`
на обычные Telegram-креды n8n.

Историю отправленного n8n держит в `$getWorkflowStaticData('global')`, поэтому файл
состояния здесь не нужен.

Команды и отклики в версию для n8n не вошли, и это ограничение самого n8n, а не недоделка.
Нода Telegram Trigger умеет работать только через `setWebhook`, то есть требует публичный
HTTPS-адрес, на который Telegram будет отправлять сообщения. Локальный n8n такого адреса
не имеет, а `getUpdates` и webhook по правилам Telegram взаимоисключающие. Поэтому
интерактивная часть живёт в скрипте, а n8n отвечает за дайджест.

Логика нод покрыта тестами (`test/n8n-workflow.test.js`): они исполняют код прямо из JSON
workflow, так что версия для n8n не может разойтись с версией для Actions незамеченной.

## Настройка под себя

Всё, что меняется без правки кода, лежит в `config.json`:

```json
{
  "queries": [
    { "text": "специалист технической поддержки", "region": "7700000000" }
  ],
  "filters": {
    "minSalary": 80000,
    "requireSalary": false,
    "maxAgeDays": 3,
    "titleKeywords": ["поддержк", "helpdesk"],
    "excludeKeywords": ["вахта", "курьер"],
    "maxExperienceYears": 1,
    "remoteOnly": false,
    "schedules": ["полный", "гибк"]
  },
  "limits": { "perQuery": 100, "maxNotificationsPerRun": 12 }
}
```

### Что вы ищете

`queries` — поисковые фразы, которые уходят в API. Чем конкретнее фраза, тем точнее выдача:
по запросу `поддержка` источник отдаёт 4759 вакансий вперемешку, по
`специалист технической поддержки` — 61, и почти все по делу. Можно перечислить несколько
запросов, результаты объединяются и дедуплицируются.

`titleKeywords` — второй, более жёсткий фильтр: вакансия проходит, только если одно из слов
есть **в названии**. Полезно, когда API притягивает лишнее: `["поддержк", "helpdesk"]` оставит
«Специалист технической поддержки» и «Инженер Helpdesk», но отбросит «Менеджер по продажам»,
даже если в его описании есть слово «поддержка». Достаточно корня слова без окончания —
`поддержк` совпадёт и с «поддержки», и с «поддержке». Пустой список отключает фильтр.

`excludeKeywords` — наоборот, отбрасывает вакансию, если слово встретилось в названии
**или** описании.

### Условия работы

`maxExperienceYears` — максимум требуемого опыта в годах. `1` оставит вакансии для новичков
и с опытом до года, `null` отключает проверку.

`remoteOnly` — только удалённая работа. Источник заполняет поле «тип занятости» лишь у трети
вакансий, поэтому признак удалёнки ищется ещё и в названии с описанием. Из-за этого фильтр
строгий: на выборке из 78 вакансий с ключевым словом «поддержк» удалённых нашлось 2.

`schedules` — допустимые графики, сверяются по части слова. В данных они записаны длинно,
поэтому пишите корень:

| Пишите | Совпадёт с |
| --- | --- |
| `полный` | Полный рабочий день |
| `гибк` | Режим гибкого рабочего времени |
| `сменная` | Сменная работа |
| `неполный` | Неполный рабочий день/неполная рабочая неделя |
| `ненормированный` | Ненормированный рабочий день |

Пустой список пропускает любой график.

### Зарплата, свежесть, объём

- `minSalary` сверяется с верхней границей вилки, поэтому «от 60 000 до 200 000» проходит порог 100 000.
  Вакансии вообще без указанной зарплаты не отбрасываются — для этого включите `requireSalary`.
- `maxAgeDays` — насколько старые вакансии ещё интересны.
- `maxNotificationsPerRun` ограничивает размер одной пачки. Остаток не теряется:
  придёт следующим запуском, пока очередь не разойдётся.
- `queries[].region` можно не указывать, тогда поиск идёт по всей стране.
  Код региона — это код ОКТМО: две цифры региона и восемь нулей. Проверенные значения:

  | Регион | Код | Регион | Код |
  | --- | --- | --- | --- |
  | Москва | `7700000000` | Санкт-Петербург | `7800000000` |
  | Московская область | `5000000000` | Новосибирская область | `5400000000` |
  | Краснодарский край | `2300000000` | Свердловская область | `6600000000` |
  | Татарстан | `1600000000` | Челябинская область | `7400000000` |
  | Нижегородская область | `5200000000` | Самарская область | `6300000000` |
  | Ростовская область | `6100000000` | Красноярский край | `2400000000` |

Расписание меняется в cron-выражении внутри `job-radar.yml`.

## Как работает дедупликация

Одна и та же вакансия приходит только один раз. Каждая отправленная запоминается по её
идентификатору (храним последние 3000), и следующие запуски её пропускают. Проверено:
второй запуск сразу после первого не присылает ничего.

Состояние живёт в `state/state.json` локально и в кэше Actions при запуске по расписанию.
**Это два независимых хранилища.** Если вы запускали радар и локально, и в Actions, каждое
из них ведёт свой список, поэтому первые пачки могут повторить друг друга. Дальше каждое
работает без дублей само по себе. Чтобы не пересекались, пользуйтесь чем-то одним — либо
локальным ботом, либо расписанием.

Окно поиска сдвигается вперёд только когда отправлено всё найденное. Если пачка не влезла
в `maxNotificationsPerRun`, остаток остаётся в том же окне и придёт следующим запуском:
иначе отложенные вакансии выпали бы из окна и не пришли бы никогда.

Запрашиваются вакансии, изменённые с прошлого раза минус шесть часов нахлёста: данные
попадают в API с задержкой, и без нахлёста часть вакансий терялась бы. Повторы,
которые из-за этого приходят, отсекаются по списку идентификаторов.

Состояние сохраняется только после успешной отправки. Если Telegram недоступен, запуск падает
с ошибкой и ничего не запоминает — те же вакансии придут в следующий раз. Выбор сделан
в пользу возможного дубля, а не потери: если дайджест разбился на несколько сообщений
и упало второе, при повторе придёт весь дайджест целиком.

С откликами противоположный приоритет: там дубль хуже пропуска, потому что повторное письмо
работодателю выглядит навязчиво. Поэтому команды подтверждаются в Telegram **до** выполнения,
журнал откликов пишется на диск сразу после отправки, а шаг коммита состояния в workflow
выполняется даже если поиск вакансий потом упал.

## Что защищает от ошибок

Бот выполняет команды только из вашего чата. Любой может найти бота и написать ему, но
сообщения с чужим `chat_id` отбрасываются — иначе посторонний мог бы отправлять письма
от вашего имени.

Перед отправкой отклик проверяется: код вакансии существует, адрес есть, письмо не пустое
и не короче 30 символов, отклик на эту вакансию ещё не отправлялся. Ограничение на длину —
защита от случайной отправки полупустого письма, которое читается как спам.

Текст письма пишете вы. Автогенерации шаблонов здесь нет намеренно: рассылка однотипных
писем по всем адресам подряд портит впечатление у тех самых работодателей и быстро упирается
в суточные лимиты почтового провайдера.

## Поставить себе

Проект рассчитан на то, что каждый запускает его со своим ботом и своей почтой.
Ничего чужого внутри нет: ни адресов работодателей, ни истории откликов — состояние
не коммитится.

1. Сделайте fork или скачайте архив.
2. `npm ci`
3. Скопируйте `.env.example` в `.env`, создайте своего бота у [@BotFather](https://t.me/BotFather)
   и впишите токен.
4. `npm run chat-id` — узнать свой `chat_id`, вписать в `.env`.
5. Для откликов добавьте `SMTP_USER` и пароль приложения почты.
6. `npm run check` — убедиться, что всё сходится.
7. `npm run bot` — работать локально, либо залить в свой репозиторий
   и прописать те же значения в **Settings → Secrets and variables → Actions**.

Поисковые запросы, пороги зарплаты и регионы меняются в `config.json` без правки кода.
